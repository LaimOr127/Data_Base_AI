# Руководство по развертыванию DIGroup для команды (50+ пользователей)

## 📋 Краткий ответ

**Да, можно развернуть для команды, но с ограничениями:**

✅ **Что работает:**
- Веб-доступ по одному адресу для всех пользователей
- Docker контейнер для простого развертывания
- Система ролей (Администратор, Редактор, Читатель)
- Аутентификация через AccessAuthCode или JWT токены

⚠️ **Ограничения:**
- **Нет встроенной системы регистрации** - пользователей нужно создавать вручную
- **Нет отслеживания автора изменений** - нельзя автоматически видеть кто что создал/изменил
- **Все пользователи с AccessAuthCode = все админы** - одинаковые права
- **JWT токены нужно генерировать вручную** - нет UI для управления

## 🐳 Вариант 1: Развертывание через Docker (Рекомендуется)

### Шаг 1: Подготовка Docker образа

```bash
# Соберите Docker образ из вашего кода
cd /Users/alexey_pripadchev/Documents/Work/data_base/siyuan
docker build -t digroup:latest -f Dockerfile .
```

### Шаг 2: Создайте docker-compose.yml

```yaml
version: '3.8'

services:
  digroup:
    image: digroup:latest
    container_name: digroup
    restart: unless-stopped
    ports:
      - "6806:6806"  # Основной порт для веб-доступа
    environment:
      - TZ=Europe/Moscow
      - PUID=1000
      - PGID=1000
    volumes:
      - ./workspace:/opt/siyuan/workspace  # Данные workspace
      - ./data:/opt/siyuan/data            # Данные приложения
    command: ["/opt/siyuan/kernel", "--workspace=/opt/siyuan/workspace", "--accessAuthCode=ВАШ_СЕКРЕТНЫЙ_КОД"]
```

### Шаг 3: Запуск

```bash
docker-compose up -d
```

### Шаг 4: Доступ

- Откройте в браузере: `http://ваш-сервер:6806`
- Введите AccessAuthCode при первом входе
- Все пользователи используют один и тот же код

```nginx
server {
    listen 80;
    server_name digroup.yourdomain.com;

    location / {
        proxy_pass http://127.0.0.1:6806;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        
        # Увеличенные таймауты для WebSocket
        proxy_read_timeout 86400;
        proxy_send_timeout 86400;
    }
}
```


## 👥 Управление пользователями и ролями

### Текущие возможности:

#### 1. **AccessAuthCode (Все админы)**

**Как работает:**
- Один код для всех пользователей
- Все получают роль Administrator
- Полный доступ ко всем функциям

**Настройка:**
```bash
# При запуске kernel
--accessAuthCode=ВАШ_СЕКРЕТНЫЙ_КОД
```

**Плюсы:**
- Простота настройки
- Все могут редактировать

**Минусы:**
- Нет разделения прав
- Нет отслеживания кто что сделал
- Все видят все документы

#### 2. **JWT токены (Разные роли)**

**Как работает:**
- Можно выдавать токены с разными ролями
- Editor - может редактировать
- Reader - только чтение

**Генерация токенов (нужно добавить в код):**

Сейчас токены генерируются автоматически для Publish Service, но можно создать скрипт для генерации:

```go
// Пример генерации JWT токена (нужно добавить в код)
token := jwt.NewWithClaims(
    jwt.SigningMethodHS256,
    jwt.MapClaims{
        "iss": "siyuan-publish-reverse-proxy-server",
        "sub": "publish",
        "aud": "siyuan-kernel",
        "jti": "username",

    },

```

**Использование:**
- Передавать токен в заголовке: `X-Auth-Token: ваш-токен`
- Или через cookie

**Ограничения:**
- Нет UI для управления токенами
- Нужно генерировать вручную
- Нет системы регистрации

## 🔍 Отслеживание автора изменений

### ⚠️ Важно: Встроенного отслеживания НЕТ

Приложение **не сохраняет** информацию о том, кто создал или изменил документ. В блоках есть только:
- `id` - уникальный ID блока
- `updated` - время обновления
- `created` - время создания (из ID)

**Нет полей:**
- `created_by` - кто создал
- `updated_by` - кто изменил

### Возможные решения:

#### 1. **Использовать атрибуты блоков**

Можно вручную добавлять атрибут `author` к блокам:
```
author: Имя Пользователя
```

Но это нужно делать вручную для каждого блока.

#### 2. **Модификация кода (для продвинутых)**

Можно добавить отслеживание автора в код:

```go
// В kernel/model/transaction.go
// При создании/обновлении блока добавлять:
node.SetIALAttr("author", getCurrentUser(c))
```

Но это требует изменения исходного кода.

#### 3. **Использовать SQL запросы**

Можно создавать SQL запросы для поиска блоков по времени обновления и сопоставлять с активностью пользователей, но это неточно.

## 📊 Производительность для 50 пользователей

### Рекомендации:

1. **Ресурсы сервера:**
   - CPU: минимум 4 ядра (рекомендуется 8+)
   - RAM: минимум 8GB (рекомендуется 16GB+)
   - Диск: SSD обязательно
   - Сеть: стабильное соединение

2. **Оптимизация:**
   - Используйте SSD для workspace
   - Настройте регулярные бэкапы
   - Мониторьте использование ресурсов

3. **Ограничения:**
   - Один kernel процесс на один workspace
   - Все пользователи работают с одной базой данных
   - WebSocket соединения для каждого пользователя

### Тестирование:

Перед развертыванием для 50 пользователей:
1. Протестируйте с 10-20 пользователями
2. Мониторьте использование CPU/RAM
3. Проверьте скорость отклика

## 🔐 Безопасность

### Рекомендации:

1. **AccessAuthCode:**
   - Используйте сложный код (минимум 16 символов)
   - Не храните в открытом виде
   - Регулярно меняйте

2. **Сеть:**
   - Используйте HTTPS (через Nginx + Let's Encrypt)
   - Ограничьте доступ по IP (firewall)
   - Используйте VPN для доступа

3. **Бэкапы:**
   - Регулярные бэкапы workspace
   - Храните бэкапы отдельно
   - Тестируйте восстановление

## ❓ FAQ

**Q: Можно ли ограничить доступ к определенным документам?**
A: Нет, все пользователи с AccessAuthCode видят все документы.

**Q: Можно ли видеть кто что изменил?**
A: Нет, встроенного отслеживания автора нет. Можно использовать атрибуты блоков вручную.

**Q: Сколько пользователей может работать одновременно?**
A: Технически неограниченно, но производительность зависит от ресурсов сервера. Для 50 пользователей нужен хороший сервер.

**Q: Можно ли использовать несколько workspace?**
A: Да, можно запустить несколько экземпляров kernel с разными workspace и портами.

**Q: Как обновлять приложение?**
A: Остановите контейнер/процесс, обновите код, пересоберите, запустите заново. Данные в workspace сохранятся.
